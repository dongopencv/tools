# docs/intake/ —— 需求入库

这里是**口述需求入库**的地方：把一次语音/随手记的原始表述，整理成可执行的需求清单。

## 为什么要有这一层

用户的原话经常来自语音转写：有错字、有同音词、有说到一半改口、有一句话里塞三个需求。
直接照着字面做，做出来的东西一定是错的——错的不是执行，是**理解**。
所以入库这一步只做一件事：把「他说的」翻译成「他要的」，并且**把翻译过程留在纸面上**，让他能一眼否掉。

## 一条需求必须写全五段

| 段 | 写什么 | 判据 |
|---|---|---|
| 原话 | 转写原文，错字照抄不修 | 能 grep 回原句 |
| 校正 | 我判断它实际指什么，以及**依据**（上下文 / 本机事实 / 同类先例） | 依据要能被核对，不能是"我觉得" |
| 实际需求 | 一句话，可执行、可验收 | 换个人读完能做出同样的东西 |
| 归属 | 落到哪张票 / 哪张图；或明确 Out of scope | 给得出编号 |
| 待确认 | 我拿不准、必须他拍板的点 | 每条都是一个是非题或选择题 |

## 硬规则

- **不改原话。** 错字是同音词的证据，改了就丢线索（"仓 CUDA"、"IP 返代"、"SQ" 全是这样捞出来的）。
- **推断必须标成推断。** 依据等级分三档：本机实测 > 仓库既有事实 > 我的猜测。第三档要显式写"猜测"。
- **一条原始表述可以拆成多条需求**，也可以一条都不成立（判定为"暂时不做"也要写下来，否则下次还得重新判一遍）。
- **不做就已经是决定。** Out of scope 的条目必须写理由，否则三个月后会被当成漏项重新提。
